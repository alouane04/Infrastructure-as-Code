IaC-1 — Terraform Codebase Guide

A complete, top-to-bottom explanation of the Terraform that provisions a highly-available AWS home for the provided NestJS todo app — plus an honest audit against the project subject.

The mission (subject scenario). Your boss handed you a USB stick with a "classic web application" and said: "Put it in the cloud, and it needs to be robust when there's traffic." This Terraform code is the answer: it builds an auto-scaling, load-balanced, multi-tier AWS infrastructure that hosts the app and survives instance loss and traffic spikes.

The shape of it. A public Application Load Balancer fronts an Auto Scaling Group of EC2 app servers running in private subnets. Those servers talk to a managed MySQL database (RDS) and a Redis cache (ElastiCache), also private. Secrets live in AWS Secrets Manager and are fetched at boot. CloudWatch watches the fleet and emails an admin via SNS when something breaks.

2. How to deploy

The whole stack comes up with three commands. The two secrets are never stored in a file — they are passed on the command line at apply time (or via TF_VAR_ environment variables).

# 1. Download the AWS provider and initialise the working dir
terraform init

# 2. Preview what will be created (optional but recommended)
terraform plan \
  -var="db_password=<choose-a-strong-password>" \
  -var="session_secret=<random-long-string>"

# 3. Build it. Type "yes" when prompted.
terraform apply \
  -var="db_password=<choose-a-strong-password>" \
  -var="session_secret=<random-long-string>"

When it finishes, Terraform prints the application URL:

Outputs:

app_url = "http://iac1-alb-123456789.eu-west-3.elb.amazonaws.com"
What you tune without touching code: everything in terraform.tfvars — the region ("Paris"), instance sizes ("small"/"medium"/"large"), the scaling range, the alert email, and the multi_az high-availability toggle. The two secrets stay on the command line.
Prerequisite gotcha (see Issue #4): the compute module reads ~/.ssh/id_rsa.pub at plan time. If that file does not exist on the machine running Terraform, apply fails before creating anything. Generate a key with ssh-keygen first, or remove that block.

To tear everything down:

terraform destroy -var="db_password=..." -var="session_secret=..."

4. Root configuration

The root directory is the "control panel." It declares the provider, defines the knobs the user turns, translates friendly names into AWS identifiers, and wires the eight modules together by passing each module's outputs into the next module's inputs.

main.tf — the wiring harness

terraform/main.tf

Pins the AWS provider (~> 5.0), sets the region from local.aws_region, and instantiates every module. The interesting part is how modules feed each other — this is the dependency graph Terraform uses to order creation:

module "compute" {
  source                    = "./modules/compute"
  app_sg_id                 = module.security.app_sg_id        # ← security
  private_app_subnet_ids    = module.network.private_app_subnet_ids  # ← network
  ec2_instance_profile_name = module.secrets.ec2_instance_profile_name # ← secrets
  target_group_arn          = module.loadbalancer.target_group_arn   # ← loadbalancer
  db_host                   = module.database.db_host          # ← database
  redis_url                 = module.cache.redis_url           # ← cache
  # ...plus secret names, sizes, scaling bounds
}

Because compute references outputs from security, network, secrets, loadbalancer, database, and cache, Terraform automatically creates those first. The resulting order is roughly:

network → security + secrets → database + cache + loadbalancer → compute → monitoring.

variables.tf — the knobs

terraform/variables.tf

Human-readable region name: "Paris", "Ireland", or "Virginia".
app_instance_size / db_instance_size / redis_instance_size
"small" / "medium" / "large". Default "small".

Auto Scaling bounds. Defaults 2 and 4.

bool — enable RDS Multi-AZ failover (true = production HA, false = cheaper). Default false.
alert_email
Where CloudWatch alarms are emailed.
project_name
Prefix for every resource name. Default "iac1".
db_password / session_secret
sensitive = true, no default — must be supplied at apply. This is what keeps them out of the repo.

locals.tf — friendly names → AWS values

terraform/locals.tf

This file is the project's answer to the subject's "use Paris not eu-west-3, small not e2-standard-1" requirement. It's pure lookup tables:

locals {
  region_map = { "Paris" = "eu-west-3", "Ireland" = "eu-west-1", "Virginia" = "us-east-1" }
  app_size_map = { "small" = "t3.micro", "medium" = "t3.small", "large" = "t3.medium" }
  db_size_map  = { "small" = "db.t3.micro", ... }
  redis_size_map = { "small" = "cache.t3.micro", ... }

  aws_region   = local.region_map[var.region]          # "Paris" → "eu-west-3"
  app_instance = local.app_size_map[var.app_instance_size]
  db_instance  = local.db_size_map[var.db_instance_size]
  redis_node   = local.redis_size_map[var.redis_instance_size]
}

terraform.tfvars — the end-user's settings

terraform/terraform.tfvars

The one file a non-expert edits. It sets non-secret values; Terraform loads it automatically. Note that db_password and session_secret are deliberately absent here.

region            = "Paris"
app_instance_size = "small"
db_instance_size  = "small"
min_instances     = 2
max_instances     = 4
alert_email       = "alouane04@email.com"
project_name      = "iac1"
multi_az          = false
redis_instance_size = "small"

outputs.tf

terraform/outputs.tf

A single output, app_url, built from the ALB DNS name so the user knows where to point their browser the moment apply finishes.

5. Module-by-module walkthrough

📦 network

modules/network/{main,variables,outputs}.tf

Purpose: the foundation everything else sits in — one VPC, three tiers of subnets across two AZs, and the routing that decides who can reach the internet.

Key resources

  • aws_vpc.main — 10.0.0.0/16, DNS hostnames + support enabled.
  • Public subnets (10.0.1/2.0/24) — host the ALB and NAT Gateway; map_public_ip_on_launch = true.
  • Private app subnets (10.0.3/4.0/24) — host the EC2 fleet; no public IP.
  • Private data subnets (10.0.5/6.0/24) — host RDS & Redis; deliberately no route to the internet.
  • aws_internet_gateway + aws_eip.nat + aws_nat_gateway (in public_a).
  • Three route tables: public → IGW; private_app → NAT; private_data → no default route (fully isolated).

Outputs

vpc_id, public_subnet_ids, private_app_subnet_ids, private_data_subnet_ids — consumed by nearly every other module.

🛡️ security

modules/security/{main,variables,outputs}.tf

Purpose: the firewall. Four security groups that form a strict chain — each tier only accepts traffic from the tier directly in front of it.

SGIngress allowed fromPort
albThe whole internet 0.0.0.0/080
appThe ALB security group only3000
rdsThe app security group only3306
redisThe app security group only6379
This SG-referencing-SG pattern (rather than CIDR ranges) is exactly the "prevent access to resources that should not be publicly accessible" requirement. The database and cache are unreachable from anywhere except the app servers.

🔐 secrets

modules/secrets/{main,variables,outputs}.tf

Purpose: store the two secrets in AWS Secrets Manager and grant the EC2 instances permission to read only those two.

Key resources

  • aws_secretsmanager_secret[.db_password / .session_secret] + their _version resources holding the actual values (recovery_window_in_days = 0 so re-applies aren't blocked by a deletion window).
  • aws_iam_role.ec2_role — assumable by ec2.amazonaws.com.
  • aws_iam_policy.secrets_read — allows GetSecretValue + DescribeSecret, scoped by ARN to just these two secrets (least privilege).
  • aws_iam_instance_profile.ec2_profile — the wrapper EC2 wears to assume the role.

The chain in one line: EC2 instance → wears → instance profile → contains → IAM role → has → policy → allows → these two secrets.

Outputs

ec2_instance_profile_name, db_password_secret_name, session_secret_name (names, not values — the values are fetched at runtime on the instance).

🗄️ database

modules/database/{main,variables,outputs}.tf

Purpose: a managed MySQL 8.0 instance — the shared source of truth for all app servers, which is what makes "changes reflected across instances" true for data.

Key resources

  • aws_db_subnet_group — pins RDS to the private-data subnets.
  • aws_db_parameter_group (mysql8.0) — sets utf8mb4 charset/collation.
  • aws_db_instance.main — engine MySQL 8.0, storage_encrypted = true, 20 GB autoscaling to 100 GB, db name todo_app, user admin, publicly_accessible = false, multi_az = var.multi_az, 1-day backups, skip_final_snapshot = true.

Outputs

db_host, db_port, db_name, db_username, db_endpoint — passed into compute so the app's .env can be built.

⚡ cache

modules/cache/{main,variables,outputs}.tf

Purpose: a single-node Redis 7 cluster, intended as a shared session store so a user stays logged in regardless of which app server the ALB routes them to.

Key resources

  • aws_elasticache_subnet_group (private-data subnets).
  • aws_elasticache_parameter_group (redis7) — maxmemory-policy = allkeys-lru.
  • aws_elasticache_cluster.main — Redis 7.0, 1 node, port 6379, no snapshots.

Outputs

redis_host, redis_port, and a ready-made redis_url (redis://host:6379).

Heads-up (Issue #3): this module is provisioned and its redis_url is injected into the app's .env, but the application code never connects to it. As wired today, Redis is unused. See the issues appendix.

⚖️ loadbalancer

modules/loadbalancer/{main,variables,outputs}.tf

Purpose: the public entry point that spreads traffic across all healthy app instances — the subject's "distribute the load evenly" requirement.

Key resources

  • aws_lb.main — internet-facing Application Load Balancer in the public subnets.
  • aws_lb_target_group.app — port 3000, health check on /health/readiness (healthy after 2 OKs, unhealthy after 3 fails, 30 s interval, expects HTTP 200).
  • aws_lb_listener.http — listens on :80, forwards to the target group.

Outputs

target_group_arn (→ compute/ASG), alb_dns_name (→ root app_url), alb_arn (→ monitoring).

🖥️ compute

modules/compute/{main,variables,outputs}.tf + user_data.sh

Purpose: the heart of the project — the self-healing, self-scaling fleet of app servers. This is where "robust under traffic" and "cattle, not pets" live.

Key resources

  • data.aws_ami.ubuntu — newest Ubuntu 22.04 from Canonical.
  • aws_key_pair.main — reads ~/.ssh/id_rsa.pub (see Issue #4).
  • aws_launch_template.app — AMI + instance type + app SG + IAM profile + the base64-encoded user_data.sh; create_before_destroy.
  • aws_autoscaling_group.app — spread across both private-app subnets, registered with the ALB target group, health_check_type = "ELB" (the LB decides health, not just EC2 status), 120 s grace, rolling instance refresh at 50% min-healthy.
  • Scaling policies + alarms: scale up +1 when CPU > 70% for 2 min; scale down −1 when CPU < 30% for 5 min.

user_data.sh — what each instance does at first boot

  1. Update Ubuntu, install Node.js 18 and the AWS CLI.
  2. Fetch db_password and session_secret from Secrets Manager using the instance's IAM role — no credentials baked in.
  3. Read its own private IP from the instance metadata endpoint.
  4. Write /opt/app/.env with DB connection, REDIS_URL, SESSION_SECRET, and SERVER_IP.
  5. npm install --production && npm run build && npm run start:prod &.

Outputs

asg_name, launch_template_id.

📈 monitoring

modules/monitoring/{main,variables,outputs}.tf

Purpose: alert the administrator when the application misbehaves — the subject's "admin must be alerted on malfunctions" requirement.

Key resources

  • aws_sns_topic.alerts + email subscription to var.alert_email (requires confirming the email AWS sends).
  • Three aws_cloudwatch_metric_alarms: unhealthy hosts > 0, 5xx errors > 10/min, response time > 2 s.
Critical (Issue #2): these three alarms set their CloudWatch LoadBalancer/TargetGroup dimensions to the full ARN instead of the required arn_suffix form. As written they will never match a metric and will never fire. Details in the appendix.

Outputs

sns_topic_arn.

6. End-to-end deploy flow

What actually happens between terraform apply and a working website:

1
Network first. Terraform sees compute depends on everything, so it builds the VPC, subnets, IGW, NAT and route tables at the base of the graph.
2
Security & secrets in parallel. The four SGs are created; the two secrets are written to Secrets Manager and the IAM role/profile are built.
3
Data & edge in parallel. RDS MySQL and ElastiCache Redis spin up in the private-data subnets; the ALB + target group + listener come up in the public subnets.
4
Compute. The launch template is rendered (it now has the DB host, Redis URL and secret names available), and the ASG launches min_instances EC2 servers across both AZs.
5
Each instance boots itself. user_data.sh installs Node, pulls the secrets via its IAM role, writes .env, builds the app and starts it on :3000.
6
Health & registration. The ALB polls /health/readiness; once an instance returns 200 twice it's marked healthy and starts receiving traffic.
7
Monitoring + output. CloudWatch alarms attach to the ASG and ALB, and Terraform prints app_url. Open it → the app responds.

8. Issues & recommendations

Severity-ordered. These are reported, not applied — the recommended fixes are for you to action.

CRITICAL · ELIMINATION CASE

#1 — Secrets committed in plaintext via Terraform state

terraform/terraform.tfstate and terraform.tfstate.backup are tracked by git (confirmed with git ls-files), and they contain the real db_password and session_secret in cleartext (the state stores secret_string values verbatim). .gitignore only excludes terraform/.terraform, not the state files.

Why it matters: the subject's Chapter VIII makes this an automatic −42: "strictly prohibited to have one or more secrets in plain text in the repository."

Recommended fix:

  • git rm --cached terraform/terraform.tfstate terraform/terraform.tfstate.backup
  • Add *.tfstate, *.tfstate.* (and *.tfvars if it ever holds secrets) to .gitignore.
  • Rotate the leaked DB password and session secret — git history still contains them until rewritten.
  • Move to a remote encrypted backend (S3 with encryption + DynamoDB state lock) so state never lives in the repo.
CRITICAL

#2 — CloudWatch alarms can never fire (wrong dimension format)

In modules/monitoring/main.tf the alarms set LoadBalancer = var.alb_arn and TargetGroup = var.target_group_arn — full ARNs. CloudWatch's AWS/ApplicationELB metrics are dimensioned by the ARN suffix, e.g. app/iac1-alb/abc123 and targetgroup/iac1-tg/def456, not the full ARN.

Why it matters: the alarms will sit in INSUFFICIENT_DATA permanently and never page anyone — so the "alert the admin on malfunction" requirement is effectively unmet despite the wiring existing.

Recommended fix: in the loadbalancer module, expose aws_lb.main.arn_suffix and aws_lb_target_group.app.arn_suffix as new outputs, pass those into monitoring, and use them in the dimensions blocks.

HIGH

#3 — Two mandatory app behaviours aren't wired through

The infrastructure injects SERVER_IP, REDIS_URL and SESSION_SECRET into each instance's .env, but the application never consumes them:

  • Server identity not shown. No template renders SERVER_IP, so "make it visible which server serves the page" (VI.1) is unmet.
  • Sessions break on refresh. web-app/src/main.ts uses Express's default in-memory MemoryStore with secret: randomBytes(42) generated per process. Behind the round-robin ALB, a refresh that lands on a different instance has no matching session, logging the user out. The provisioned Redis would solve this but is unused.

Recommended fix (app side — modifying the app is explicitly permitted by the subject): wire express-session to a Redis store (e.g. connect-redis) using REDIS_URL, set secret from SESSION_SECRET, and surface SERVER_IP in a view/footer. Then the already-built Redis and shared secret start doing their job.

MEDIUM

#4 — SSH key file dependency breaks portable deploys

modules/compute/main.tf does public_key = file("~/.ssh/id_rsa.pub"). On any machine without that file (CI, a teammate, a fresh laptop), terraform apply fails immediately. And the key is functionally useless anyway: the app SG opens no port 22, instances have no public IP, and there's no bastion — so nobody can SSH in regardless.

Recommended fix: either drop the key pair entirely (instances are managed cattle, not pets — use SSM Session Manager if access is needed), or make the public key a variable with a sensible default so deploys don't depend on a local file.

MEDIUM

#5 — Single NAT Gateway is a single point of failure

One NAT Gateway lives in public_a, and both private-app route tables point at it. If AZ-A degrades, app instances in AZ-B lose all outbound internet — meaning new instances there can't fetch secrets or run npm install at boot.

Assessment: this is a defensible cost tradeoff — the subject heavily emphasises cost ("less than five euros", "cattle not pets"), and a second NAT roughly doubles the standing cost. Keep it for the minimal-cost profile, but document it; for a true-HA profile, add one NAT per AZ with per-AZ route tables.

MINOR / POLISH

#6 — Small things worth tidying

  • Placeholder alert email (alouane04@email.com) — set a real, monitored address, and remember to confirm the SNS subscription email.
  • Typos in descriptions — "Enabl Multi-AZ" (database vars), "recive" (root alert_email). Cosmetic only.
  • Hardcoded AZ suffixes — subnets assume ${region}a / ${region}b exist. True for the three supported regions, but data.aws_availability_zones would be more robust.
  • Readiness check pings the DB. /health/readiness includes a DB ping; a brief DB blip can mark every instance unhealthy at once. Consider separating liveness (already present) from readiness for the LB.
  • HTTP only. No TLS/HTTPS — but the subject lists HTTPS as a bonus, so this is fine for the mandatory part.

Scope of this guide: documents the Terraform under terraform/ as it currently stands and audits it against en.subject.pdf. No code, configuration, or git state was modified in producing it. All recommended fixes are advisory.
